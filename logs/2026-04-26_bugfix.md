# 2026-04-26 deckpilot daemon "hang" investigation

## TL;DR

The user-applied "暫定対処" (`git revert 9421f29` + rebuild) **did not fix any
bug** because `9421f29` only added markdown files under `.dispatch/` and `logs/`
— it touched zero Go code. What restored `deckpilot ls` etc. was the *rebuild*,
which incidentally caused a fresh `daemon` subprocess to be started by
`daemon.EnsureRunning()`. The pre-rebuild daemon was simply an old, stuck process.

The forward fix lands two real defects introduced by `26e3cff`
("feat(hang): add non-destructive recovery and cleanup command") and one
architectural fix that addresses the user-visible symptoms:

1. **`hang-detect --on-hang recover|tiered-recover` was advertised but never
   wired.** `pickHangAction`'s switch returns `unknown action` for those values
   while the usage string and the unrelated `recoverActionForSession` helper
   pretend they are valid. Either wire it (interactive `fmt.Scanln` makes that
   wrong for an unattended monitor) or stop advertising it.
2. **`main.go` `cleanup` case is mis-indented** (mixed tabs+spaces) — `gofmt`
   complains, the `default:` help message also doesn't list `cleanup`/`hang-detect`.
3. **`pipe.Discover` serially `Ping`s every running `ghostty.exe` PID with a
   2 s dial + 5 s read deadline (worst case 7 s per PID).** With ≥2 stuck
   ghostty processes the daemon's `LIST` handler can blow past the 10 s
   `handleConn` deadline → client sees `list: no response from daemon`. Same
   path is invoked by `launch`'s `waitForNewSession` and explains the
   `session detect: no new session detected within 15s` symptom.

Decision: **keep the revert** (`ec52b03`) — the dispatch/logs notes are
historical artefacts, not source. Re-adding them is not necessary, but they're
also not harmful. We do not re-apply `9421f29`.

### What `26e3cff` actually changed
Substantive code changes:
- `cmd/cleanup.go` (new) — `Cleanup()` removes hang dumps older than N days.
- `cmd/hangdetect.go` — default `--on-hang` flipped from `notify` → `snapshot`,
  added `recoverActionForSession` *but never wired into `pickHangAction`*, and
  changed the usage strings to advertise `recover` / `tiered-recover` that the
  switch does not handle.
- `cmd/launch.go` — `findGhostty` → `FindGhostty` (exported); added
  `SpawnGhostty()` for the unwired recover path.
- `main.go` — added `cleanup` case (mis-indented), updated help text.

Plus a large amount of cosmetic damage from a Codex-style rewrite: LF→CRLF
mass-replace and en-dash / em-dash UTF-8 mangling (`–` → `Eonce`,
`→` → `ↁE`). These do not break the build but make future diffs noisy.

### What is actually causing the symptoms

`deckpilot ls` → `list: no response from daemon`: the daemon-side handler
calls `refreshSessions()` → `pipe.Discover()` → `discoverFromProcesses()`,
which iterates every `ghostty.exe` PID and synchronously calls
`pipe.Ping()` (`pipe/client.go:174`). Each `Ping` uses
`dialTimeout = 2 s` + `readDeadline = 5 s`. When a ghostty process is hung at
the OS level, both the dial and the read consume their full budget — so
`refreshSessions` becomes O(N × 7 s). The IPC handler sets
`conn.SetDeadline(time.Now().Add(10 * time.Second))` (`daemon/ipc.go:30`), so
two stale ghostty processes are enough to exceed it.

`launch ... → no new session detected within 15s`: same path. The
`waitForNewSession` loop polls `listSessionNames()` every 500 ms with a 15 s
deadline (`cmd/launch.go:191`). When `pipe.Discover` is taking 7-21 s per
attempt, the loop barely manages 1-2 polls, and a freshly-launched ghostty's
session file may not have been re-discovered before the deadline.

`submit_failed_stuck|402ms` is **not** a daemon bug per se — it is the
correct, designed response from `ConfirmSubmit` when the *target* TUI does not
echo the typed text (because the target ghostty is hung). The fix for that is
to keep the daemon responsive long enough for `hang-detect` to decide what to
do (snapshot / Ctrl+C / external recover), which loops back to fix #3 above.

## Phase 2 — Pattern analysis

`pipe.Discover` already has a fast-path / fallback structure
(`discoverFromProcesses` then `discoverFromSessionFiles`). The session-files
path validates each candidate via `Ping`/`PingWS` *and is also serial*, so the
same hazard exists on the fallback side.

The two existing tests in `pipe/enrich_test.go` cover the field-merging
contract, not discovery latency or concurrency, so this is uncovered today.

## Phase 3 — Hypothesis

Hypothesis: parallelizing the per-PID `Ping` and giving discovery a hard
budget will collapse the worst-case `Discover()` latency from `O(N × 7s)` to
roughly `max(per_pipe_ping)` ≤ 7 s, and a tighter discovery-only timeout will
keep it well below the 10 s IPC deadline.

## Phase 4 — Fix

### Code changes

- `pipe/discovery.go` — `discoverFromProcesses` now uses
  `probePIDsConcurrent`, a small helper that fans out one goroutine per
  PID and collates results in PID-input order. The single-PID probe
  body moved into `probePID(pid)` so it is testable in isolation.
- `pipe/discovery_concurrent_test.go` — new tests:
  - `TestProbePIDsConcurrent_RunsInParallel` — 5 × 200 ms fake probes
    must finish in <600 ms (serial would be 1 s).
  - `TestProbePIDsConcurrent_OneSlowProbeDoesNotStallOthers` — one
    500 ms probe must not push fast probes past 200 ms from start
    (regression-pin for the 2026-04-26 outage shape).
  - `TestProbePIDsConcurrent_DropsFailures`,
    `TestProbePIDsConcurrent_EmptyInput` — contract guards.
- `cmd/hangdetect.go` — dropped the unwired `recover` / `tiered-recover`
  options from the usage string and the `pickHangAction` switch error
  message; deleted the unused `recoverActionForSession` helper. The
  helper called `fmt.Scanln` from inside the hang-action callback,
  which would block an unattended monitor on stdin.
- `cmd/launch.go` — deleted the `SpawnGhostty` helper that only
  existed to back the removed recover action.
- `cmd/cleanup.go` — fixed a docstring lie ("Default age is 7 days"
  vs. the actual `3 * 24 * time.Hour`).
- `main.go` — fixed mixed-tabs/spaces indentation around the
  `cleanup` switch case and added `hang-detect`/`cleanup` to the
  unknown-command help line so the CLI surface is consistent.

Note on `9421f29`: the revert (`ec52b03`) is kept. The dispatch
markdown notes are not source-of-record artefacts, the path-check
bypass commit message proved misleading, and re-applying the commit
would carry no functional change.

### Roll-out note

The running daemon is still the pre-fix process — `pipe.Discover`'s
serial behavior is baked into the binary that backs the daemon
goroutine. To pick up the fix without disturbing live sessions, the
operator runs `deckpilot shutdown && deckpilot ls` (the second call
re-spawns the daemon via `EnsureRunning`). Ghostty session processes
are independent of the daemon, so they are not affected. We do not
trigger the restart automatically here because another agent is
currently driving `ghostty-10300`.
